# فاز جدید آوان: ProcessMaker Sync، چارت سازمانی، مدیریت سامانه و لایسنس

**وضعیت: کدنویسی فاز زیرساخت در مخزن انجام شده؛ اما اتصال زنده به ProcessMaker/Keycloak و اجرای اسکریپت‌های جدید SQL روی رایانه مشتری هنوز انجام و تأیید نشده است.**
تمام SQL این فاز فقط روی دیتابیس جداگانه `EnterpriseProcess2_AI_Test` مجاز است. بانک‌های عملیاتی `EnterpriseProcess` و `EnterpriseProcess2` و فرم‌های ProcessMaker مطلقاً نباید با این فایل‌ها تغییر کنند.

## الگوی مرجع Organization Portal

ساختار مرجع در ریپازیتوری `HamidrezaNoee/organization-portal` بررسی شده است: Keycloak و OIDC، ASP.NET Core BFF با نشست HttpOnly و ضد CSRF، نقش‌های `GodAdmin` و `SysAdmin`، سرویس مدیریت حساب و ابزار آفلاین LIMAK License Studio با امضای ECDSA P-256 و کلید خصوصی خارج از سرور مشتری. ماژول احراز هویت فعلی آوان اعتبارسنجی RS256 Keycloak/IdP و یک پنل آزمایشی SPA با OAuth PKCE را دارد، اما **هنوز BFF معادل و استقرار واقعی Keycloak سازمان پیاده یا آزمایش نشده است**. بنابراین «همان auth» از نظر پروتکل هویت و نقش‌ها هدف طراحی است، نه ادعای برابری امنیتی/عملیاتی نشست‌ها.

## نقش‌ها و مرز مجوزها

| نقش | دامنه دسترسی |
| --- | --- |
| Expert / کارشناس | جلسات دارای مجوز مستقیم یا حضور خود/زیرمجموعه به‌عنوان دبیر، رئیس، شرکت‌کننده، مسئول اقدام. نامه‌های عادی متعلق به خود/افراد زیرچارت؛ نامه محرمانه فقط مالک یا دارای مجوز صریح. |
| Manager / مدیر | تمام جلسات سازمان خودش، حتی بدون حضور مستقیم؛ گزارش اقدامات همان سازمان؛ نامه‌های محرمانه صرف نقش مدیر افشا نمی‌شوند. |
| SysAdmin / مدیر سیستم سازمان | دسترسی مدیر به محتوای همان سازمان، به‌علاوه مدیریت چارت، نقش‌های Expert/Manager، تنظیمات نام/رنگ/لوگو و همگام‌سازی کنترل‌شده کاربران ProcessMaker؛ **مجوز SysAdmin جدید را خودش صادر نمی‌کند**. |
| GodAdmin / مدیر کل پلتفرم | مدیریت فهرست سازمان‌ها، ایجاد سازمان غیرفعال، فعال‌سازی لایسنس معتبر و فراداده پلتفرم. نقش GodAdmin به‌تنهایی دسترسی به جلسات/اسناد/نامه‌های محرمانه سازمان‌ها نمی‌دهد. نیازمند نقش امضاشده Keycloak + ثبت جداگانه `PlatformOperator` است. |

در حال حاضر `/v2/meetings/page`, `/v2/secretary/preparation/{meeting_id}`, `/v2/analytics/action-overview` و `/v2/monitoring/overdue` بر اساس هویت لینک‌شده، نقش سازمانی و چارت، جدا از API قدیمی `/v1` پیاده شده‌اند. جداول MeetingActor باید بعداً با شناسه‌های واقعی دبیر، رئیس و اقدام‌کنندگان از منابع مورد تأیید تطبیق و با فرآیند ETL کنترل‌شده وارد شوند. **تا پیش از این مرحله، دیدن نشست‌های واقعی زیرمجموعه در محصول ممکن نیست.** سناریوهای تست `22` صرفاً ساختگی‌اند.

## همگام‌سازی ProcessMaker

آداپتر `commercial/processmaker_directory.py` فهرست کاربران را با OAuth دسترسی خواندنی، صفحه‌بندی و سقف ۵۰۰۰ حساب از ProcessMaker می‌گیرد. همه فیلدهای نامربوط، از جمله رمز یا هش رمز `usr_password`، کنار گذاشته می‌شوند. شناسه ثابت کاربر ProcessMaker (PMUserUID) کلید همگام‌سازی است، نه نام یا ایمیل. Snapshot ناقص/تکراری رد می‌شود؛ کاربر تازه به حالت `IsEnabled=0` و بدون پیوند به `sub` سرویس هویت وارد دایرکتوری می‌شود. Sync به‌طور خودکار نقش مدیر، SysAdmin، GodAdmin، مدیر مستقیم یا رمز ورود را تعیین نمی‌کند.

`GET /v2/admin/processmaker/users/preview` فقط پیش‌نمایش خواندنی است؛ `POST /v2/admin/processmaker/users/sync` صرفاً پس از تأیید هویت SysAdmin در Keycloak و دیتابیس و اتصال امن حساب SQL نویسنده مجزا قادر به تغییر *دایرکتوری آزمایشی* است. گزینه غیرفعال‌کردن افراد غایب در خروجی منبع، پیش‌فرض **خاموش** دارد؛ تا کنترل کامل‌بودن API واقعی PM و تأیید سیاست منابع انسانی آن را روشن نکنید.

**محدودیت باقی‌مانده:** مشخصات اتصال واقعی، کلید دسترسی خواندنی ProcessMaker، mapping `sub` Keycloak به UIDهای موجود، فرآیند صدور حساب/بازیابی رمز امن و استقرار BFF هنوز تنظیم/آزمایش نشده‌اند. رمزهای سرویس را در چت، GitHub یا HTML قرار ندهید.

## SQL فقط در محیط آزمایشی — فاز نصب جداگانه

در SSMS با TEST DBA و هر فایل در **New Query مستقل** اجرا شود. این فایل‌ها بر بانک عملیاتی اثر ندارند؛ اما جداول جدید در بانک آزمایشی می‌سازند. پس از اولین خطا متوقف شوید و دوباره بی‌هدف اجرا نکنید.

1. `commercial/sql/19_directory_hierarchy_TEST_ONLY.sql` — ساخت دایرکتوری، چارت، نقش‌های جلسه و نمایه نامه؛ بدون ورود اطلاعات واقعی.
2. `commercial/sql/20_processmaker_sync_TEST_ONLY.sql` — پروسیجر همگام‌سازی؛ هیچ ProcessMaker واقعی فراخوانی نمی‌شود.
3. `commercial/sql/21_directory_admin_TEST_ONLY.sql` — تغییر مدیر مستقیم و نقش Expert/Manager با کنترل حلقه و Audit.
4. `commercial/sql/22_seed_directory_lab_TEST_ONLY.sql` — **فقط یک بار**، Alice/Bob/Manager/Admin/Carol ساختگی برای تست چارت و ۱۰۲ جلسه قابل رؤیت Alice.
5. `commercial/sql/23_platform_control_TEST_ONLY.sql` — ثبت GodAdmin **بدون ایجاد اپراتور خودکار**، فهرست فراداده سازمان‌ها و لایسنس.
6. `commercial/sql/24_tenant_branding_TEST_ONLY.sql` — تغییر نام و رنگ سازمان.
7. `commercial/sql/25_letter_acl_TEST_ONLY.sql` — ACL نامه؛ **هیچ نامه واقعی وارد نمی‌شود**.
8. `commercial/sql/26_tenant_logo_TEST_ONLY.sql` — نگهداری نام لوگوی محدود و ثبت Audit.
9. `commercial/sql/27_admin_login_permissions_TEST_ONLY.sql` — **تنها پس از** ایجاد دستی دو SQL LOGIN مستقل و کم‌دسترسی (`AI_CommercialDirectoryAdmin` و `AI_CommercialPlatformAdmin`) و اجرای مراحل قبل؛ این فایل رمز یا LOGIN مدیریتی نمی‌سازد.

حساب `AI_CommercialReader` قبلی هیچ مجوزی برای اجرای پروسیجرهای مدیریتی دریافت نمی‌کند. رمزهای سه حساب SQL باید مستقل و خصوصی بمانند. برای اجرای واقعی پنل جدید، GodAdmin در Keycloak و سپس با احراز اصالت شناسه `sub` در PlatformOperator ثبت می‌شود. هیچ شناسه یا حساب GodAdmin در این SQLها به‌صورت پیش‌فرض ایجاد یا تأیید نشده است.

## لایسنس مستقل مشابه الگوی مرجع

`commercial/licensing/studio.py`: نسخه اولیه ابزار آفلاین ویندوز (Tkinter + خط فرمان) برای ساخت کلید خصوصی رمزدار ECDSA P-256 بیرون از Git/سرور مشتری و صدور توکن امضاشده برای TenantID، InstallationID شصت‌وچهاررقمی، نام مشتری، سقف کاربر فعال، ماژول‌های ۱ تا ۴ و تاریخ انقضا/نامحدود. تنها کلید عمومی روی سرور محصول نصب می‌شود.

```powershell
$repo = "D:\A Project\17 meeting ai agent\Azure\AI-Agent-Lab-GitHub"
$python = "D:\A Project\17 meeting ai agent\Azure\AI-Agent-Lab\.venv\Scripts\python.exe"
git -C $repo pull --ff-only origin main
cd $repo
& $python -m commercial.licensing.studio
```

برای نمونه **آزمایشی**، ابزار بدون ذخیره یا ارسال رمز در Git باید کلید و سپس لایسنس را روی رایانه امن صادرکننده ایجاد کند. صدور لایسنس پرداخت، فعال‌سازی لایسنس در مشتری و محدودیت ظرفیت کاربر هنگام افزودن حساب هنوز نیازمند آزمون عملیاتی با Keycloak/SQL هستند. `COMMERCIAL_REQUIRE_SIGNED_LICENSE=1` پس از نصب کلید عمومی و ثبت لایسنس واقعی، درخواست‌های بدون مجوز معتبر را رد می‌کند؛ **قبل از آماده‌سازی آن تنظیم نشود**.

## آنچه هنوز کامل نیست

- اتصال زنده ProcessMaker و نگاشت واقعی جلسه/دبیر/رئیس/مسئول اقدام و نامه از منبع مجاز.
- BFF با Cookie امن و CSRF مشابه کامل Organization Portal، ثبت OAuth client و MFA/Keycloak واقعی، انتساب مورد تأیید `sub` به DirectoryUser.
- ایجاد کاربر Keycloak، بازنشانی رمز، بوت‌استرپ GodAdmin و SysAdmin از مسیر تأییدشده؛ نمایش بخش مدیریتی **جایگزین راه‌اندازی امن این قابلیت‌ها نیست**.
- تنظیم رمز/میزبان SQL و PM از طریق رابط وب: اکنون فقط وضعیت ماسک‌شده نمایش داده می‌شود؛ ویرایش اسرار نیازمند سرویس امن جداگانه است.
- اتصال واقعی صندوق نامه، اعمال مجوز بر تمام ابزارهای LLM و اسناد واقعی، آزمون جامع نفوذ/کارایی، پرداخت/فعال‌سازی لایسنس در محیط مشتری.
- هیچ یک از SQLهای ۱۹ تا ۲۷ روی رایانه شما اجرا یا تأیید نشده‌اند و CI GitHub Actions در این مرحله قبل از ثبت خروجی گام‌ها Fail شده است. آزمون جدیدی را پاس‌شده تلقی نکنید تا اجرای محلی/CI مستند شود.
