# اجرای دو فرایند نسخه ۷ در آوان

این نسخه از دو فایل ارسال‌شده در ۱۴۰۵/۰۷/۱۲ ساخته شده است:

| فرایند | شناسه | SHA-256 محتوای XML |
|---|---|---|
| مدیریت جلسات | `f7f263ea31d8731d212820f220c65a48` | `4b57d961c95d2e201393cfd4458b4cf42fa5c70ba9dd20362cdc6ff9bbe6f0a0` |
| اقدام مصوب جلسه | `cd66870095907431106b6dd110e06fa7` | `e3027dcfce497baaf547a9ee9c9797a1d54a1b194ea666cde02021b544d06ee5` |

فایل‌های اصلی تغییر نکرده‌اند. بسته فقط قرارداد فرم‌ها، نگاشت وظایف و اثرانگشت
تریگرها را نگه می‌دارد. کد PHP در آوان اجرا نمی‌شود؛ تریگرها روی ProcessMaker
و با REST حساب متصل اجرا می‌شوند. فعال‌سازی، تطابق فرم‌ها، ترتیب تریگرها و
اثر انگشت کد ۱۴ تریگر استفاده‌شده را با نصب مقصد بررسی می‌کند.

## به‌روزرسانی در PowerShell

در پوشه نصب فعال، ابتدا تغییرات محلی خود را بررسی کنید:

```powershell
git status --short
git switch feature/pm-native-agent-store-20260922
git pull --ff-only origin feature/pm-native-agent-store-20260922
docker compose ls
.\scripts\update-avan-meetings.ps1 -ProjectName avan-production -ComposeFiles @('compose.yaml','compose.pm-local.yaml') -IncludeIdentity
```

نام پروژه و فایل‌های Compose باید دقیقاً همان نصب فعلی باشند. اگر HTTPS دارید،
همان `compose.https.yaml` و سایر overlayهای نصب را بدهید. اسکریپت اگر کانتینر
نصب موجود را پیدا نکند متوقف می‌شود. دیتابیس‌ها/antibot باید از قبل آماده باشند.
نیازی به حذف Volume، تولید دوباره secret، ساخت دوباره کاربران یا واردکردن مجدد
PMX روی پرونده‌های فعال نیست. اگر نسخه نصب‌شده متفاوت است، ابتدا تفاوت را بررسی
کنید؛ واردکردن کورکورانه PMX ممکن است به پرونده‌های فعال آسیب بزند.

## فعال‌سازی در آوان

۱. مدیریت سامانه ← اتصالات BPMS ← تنظیم فرایند همان اتصال.
۲. «فعال‌سازی بسته آماده جلسات و اقدامات — نسخه ۷» را بزنید. اگر هر دو کارتابل
قبلاً خواندنی بودند، در یک تراکنش به بسته مشترک ارتقا پیدا می‌کنند. تغییر هم‌زمان
مدیر دیگر باعث رد درخواست و الزام تازه‌سازی می‌شود.
۳. کاربر MySQL باید فقط SELECT داشته باشد؛ علاوه بر داده‌های پرونده، برای بررسی
بسته به `PROCESS`, `TASK`, `DYNAFORM`, `STEP`, `STEP_TRIGGER`, `TRIGGERS` دسترسی خواندن لازم است.
۴. در کاربران، دسترسی ماژول جلسات/دبیر و اتصال صریح حساب هر فرد به کاربر همان
BPMS را تنظیم کنید. گروه و تخصیص وظیفه در ProcessMaker همچنان تعیین‌کننده است.
۵. هر فرد در کارتابل خود مجوز اجرای فرایند را با OAuth حساب خودش متصل کند.
توکن مدیریتی اتصال جایگزین مجوز شخصی کاربر نمی‌شود.
۶. اتصال AI را در تنظیمات آوان آزمایش کنید. پیشنهاد AI پیش‌نویس است؛ داده ناقص
یا هویت نامشخص باید تکمیل شود. برای ورودی بزرگ، فرم دستی همچنان قابل استفاده است.

نشانی پایه سرور شما `http://automation.iranroverholding.com:81` است.
Workspace، OAuth client و MySQL host/port را از نصب واقعی بگیرید؛ پورت HTTP شماره
۸۱ به معنی پورت MySQL نیست. نام workspace از نشانی ورود PM یا تنظیمات نصب مشخص
می‌شود؛ در این تغییر مقدار حدسی برای نصب شما ذخیره نشده است.

## پیش‌نیاز شماره‌گذاری جلسه در دیتابیس Workspace

Trigger آغاز فرم دعوت برای تولید `MTG_MeetingNo` به جدول
`MTG_MEETING_SEQUENCE` در دیتابیس Workspace خود ProcessMaker وابسته است.
این جدول داده عملیاتی شماره‌گذاری است و SQL Server نیست. اگر جدول وجود نداشته
باشد، ProcessMaker اجرای BEFORE Trigger را با HTTP 400 رد می‌کند.

مهاجرت idempotent آماده در مسیر زیر قرار دارد:

`scripts/processmaker/ensure-mtg-meeting-sequence.sql`

این فایل باید یک‌بار توسط حساب مدیریتی MySQL روی همان دیتابیس Workspace
(برای نمونه `bitnami_pm`) اجرا شود. AVAN عمداً این DDL را با اتصال خواندنی خود
اجرا نمی‌کند. پس از ایجاد جدول، حساب خواندنی مورد استفاده AVAN نیز باید حداقل
مجوز `SELECT` روی `MTG_MEETING_SEQUENCE` داشته باشد تا preflight قبل از ساخت
Case بتواند آماده‌بودن زیرساخت را تأیید کند.

## نقشه جریان پرونده‌ها

میز کار دبیر هوشمند یک نمای Read-only با عنوان «نقشه جریان پرونده‌ها» دارد.
این نما برای هر جلسه‌ای که شخص انتخاب‌شده در آن نقش داشته است، مسیر هفت‌مرحله‌ای
جلسه را به شکل Git-like نمایش می‌دهد و هیچ تغییری در ProcessMaker ایجاد نمی‌کند.

مبنای داده:
- `APPLICATION.APP_DATA` برای عنوان، شماره جلسه و نقش‌های جلسه؛
- `APP_DELEGATION` برای مرحله و مسئول فعلی؛
- UIDهای Task از قرارداد بازبینی‌شده `meeting_v2`، نه عنوان متنی Task؛
- `MTG_ActionCaseMapJson` برای اتصال پرونده‌های اقدام به پرونده جلسه.

فیلترهای فعلی: شخص، بازه زمانی، نقش در پرونده، وضعیت، مرحله فعلی، مسئول فعلی،
واحد سازمانی و جستجوی شماره/عنوان. تغییر شخص فقط در دامنه مجاز همان حساب AVAN
امکان‌پذیر است. KPIهای بالای گزارش نیز بر اساس فیلتر جاری محاسبه می‌شوند.

API:
`POST /api/sources/{source_id}/secretary/flow-graph`

## پذیرش عملکردی با سه حساب واقعی

| مرحله | مسئول | رفتار و آزمون |
|---|---|---|
| برنامه‌ریزی و دعوت | دبیر | متن/فایل به پیش‌نویس؛ رفع نواقص؛ ایجاد شماره توسط PM و ارسال دعوت |
| بررسی دعوت | رئیس | انتخاب تأیید یا نیاز به اصلاح؛ در حالت اصلاح، توضیح اجباری |
| صورت‌جلسه | دبیر | مذاکرات، مصوبات، مسئول و مهلت؛ تشکیل‌نشدن نیازمند علت |
| بررسی صورت‌جلسه | رئیس | رأی صریح و ارسال؛ ایجاد اقدامات توسط تریگر نصب‌شده PM |
| اجرای اقدام | اقدام‌کننده | گزارش پیشرفت یا ادعای تکمیل؛ تکمیل درصد را ۱۰۰ می‌کند |
| بررسی اقدام | دبیر | بررسی گزارش/مدرک؛ اصلاح درصد یا برگشت با توضیح؛ AI فقط پیشنهاد می‌دهد |
| پایش و اختتام | دبیر | جمع‌بندی، بررسی اقدامات، اختتام یا پیشنهاد پیگیری |

آزمون‌های منفی: حساب نامرتبط، تغییر تخصیص، پیش‌نویس قدیمی، دوبار ارسال، ورودی
بیش‌ازحد، مدرک ساختگی و تصمیم بدون داده ضروری باید رد شوند. در timeout عملیات PM،
وضعیت نیازمند تطبیق نگه داشته می‌شود؛ ارسال خودکار مجدد انجام نمی‌شود.

ورود فایل متن/PDF/DOCX برای استخراج اطلاعات و خواندن اسناد موجود PM پشتیبانی
می‌شود. ورود فایل برای AI به‌تنهایی به معنی بارگذاری فایل اصلی در اسناد PM نیست؛
انتقال فایل اصلی به PM باید جداگانه روی نصب واقعی بررسی و تکمیل شود.

## هزینه AI و حدود اثبات

درخواست استخراج فقط قرارداد مرحله، مقادیر فعلی، زمینه مرتبط و حداکثر ۸۰ فرد
مرتبط را می‌فرستد؛ ایمیل و اطلاعات اضافی دفترچه حذف می‌شوند. سقف ورودی ۴۸ هزار
نویسه و خروجی ۳۵۰۰ توکن است. ورودی بزرگ بدون قطع پنهانی داده رد می‌شود. شمارش
نویسه معادل شمارش دقیق توکن نیست و صرفه‌جویی درصدی ادعا نشده است.

تست هفت مرحله، runtime واقعی و آداپتور HTTP آوان را با پاسخ شبیه‌سازی‌شده PM
اجرا می‌کند. اجرای PHP، ارسال واقعی پرونده، OAuth واقعی، مدل پولی و نتیجه روی
سرور سازمان باید با حساب‌های واقعی تأیید شود؛ هیچ نقش یا پرونده زنده‌ای از این
محیط تغییر نکرده است.

## نمای جدید دبیر هوشمند

«دعوت جلسه» تنها شروع مستقل است. هفت مرحله به ترتیب نمایش داده می‌شوند؛
مرحله بدون پرونده غیرفعال است و نشان تعداد ندارد. نشان‌ها فقط از کارتابل فعلی
همان حساب/اتصال/بسته می‌آیند، نه تعداد کل پرونده‌های سازمان. هر مرحله فهرست
وظایف خودش را فیلتر می‌کند. فرم OAuth جمع‌شده، دعوت‌های قبلی جدا و مرحله جاری
در صفحه گفت‌وگو مشخص است. نمای دسکتاپ، موبایل و ورود به وظیفه با API آزمایشی
در مرورگر بررسی شده‌اند. پس از به‌روزرسانی Ctrl+F5 بزنید.
